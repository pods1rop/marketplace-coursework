## Аннотация

В курсовом проекте разработан прототип программной системы маркетплейса товаров, ориентированного на продажу новых и second-hand/винтажных позиций. Система объединяет в единой площадке покупателей, продавцов, модераторов и администраторов: покупатель работает с каталогом, корзиной, избранным и заказами; продавец публикует и сопровождает свои товары; модератор контролирует контент перед публикацией; администратор управляет ролями и наблюдает статистику. Серверная часть реализована на Java 17 и Spring Boot 3.2; данные хранятся в реляционной СУБД MySQL и доступны через Spring Data JPA. Пользовательский интерфейс построен на основе серверного рендеринга шаблонов Thymeleaf, оформленных с помощью утилитарного CSS-фреймворка Tailwind, и дополнен AJAX-фильтрацией каталога, динамическими каруселями и анимированными счётчиками. Подлинность учётных записей и разграничение доступа обеспечивается Spring Security с формой входа и хеш-функцией BCrypt.

## Annotation

The course project presents a prototype of a marketplace platform for new, second-hand and vintage goods. The system unites four user roles — buyer, seller, moderator and administrator — within a single platform: buyers work with the catalogue, cart, favourites and orders, sellers list and manage their items, moderators review submitted content before it is published, and administrators manage roles and watch overall statistics. The server side is built on Java 17 and Spring Boot 3.2; data is stored in MySQL and accessed through Spring Data JPA. The user interface uses server-side Thymeleaf templates styled with the Tailwind CSS utility framework, complemented by AJAX-based catalogue filtering, dynamic carousels and animated counters. Authentication and role-based access are provided by Spring Security with form login and BCrypt password hashing.

## Введение

Рынок частных продаж в России активно перетекает в онлайн: пользователи ищут как новые товары по выгодной цене, так и редкие вещи у частных продавцов — винтажную одежду, коллекционные кроссовки, бывшую в употреблении электронику. Классические доски объявлений (Avito, Юла) дают огромную аудиторию, но не предоставляют покупателю единой корзины, оформления заказа в один шаг и стандартизованной системы рейтингов. Крупные маркетплейсы (Wildberries, Ozon) удобны для покупки, но фактически закрыты для индивидуальных продавцов и не работают с категорией second-hand. В результате пользователи вынуждены распределять покупки между несколькими разнородными платформами и держать в голове особенности каждой.

Поэтому актуальной становится разработка собственной площадки, которая совмещает плюсы обоих миров: каталог и корзину как у крупного маркетплейса, низкий порог входа и широкий ассортимент как у досок объявлений, а также прозрачную модерацию и систему отзывов для повышения доверия. Решению этой задачи и посвящён курсовой проект.

## 3. Проектирование системы

### 3.1 Диаграммы UML уровня проектирования

Поведение системы описано диаграммой прецедентов (рисунок 2), на которой выделены четыре актора: гость, покупатель, продавец и сотрудник платформы (модератор/администратор). Прецеденты сгруппированы по ролевым областям: «Просмотр и поиск товара», «Покупка», «Управление каталогом продавца», «Модерация и администрирование». Прецеденты регистрации, входа и оформления заказа явно показывают расширения для альтернативных потоков (ошибка валидации, повторный email, отмена оформления).

Структура данных серверной части отражена на концептуальной диаграмме классов (рисунок 3). Центральная сущность — Product (товар) — связана с категорией (Category), брендом (Brand), продавцом (User), отзывами (Review), элементами корзины (CartItem) и заказа (OrderItem), а также с дополнительными изображениями (ProductImage). Перечисления статуса публикации, состояния (NEW/USED/VINTAGE), пола целевой аудитории и сезона хранятся в самой сущности Product как строковые перечисления, что упрощает добавление новых значений миграцией.

Жизненный цикл заказа описан диаграммой состояний (рисунок 4): NEW → PAID → SHIPPED → DELIVERED, с возможностью перехода в CANCELLED из первых двух состояний. Аналогичная диаграмма (рисунок 5) показывает состояния товара как объекта модерации: PENDING → APPROVED либо REJECTED, с возможностью повторной подачи после правок и переход в REMOVED при снятии товара продавцом.

### 3.2 Описание слоёв программы

Серверная часть построена по классической трёхслойной архитектуре «контроллер — сервис — репозиторий» с дополнительным слоем DTO для передачи данных в шаблоны и AJAX-эндпоинты.

**Слой репозиториев** обращается к MySQL через Spring Data JPA. Для часто используемых выборок (товары по фильтру, заказы продавца, отзывы по товару) применяются методы со спецификациями и постраничным выводом `Pageable`. Чтобы при отображении каталога не возникала проблема N+1 запросов, в выборках товаров используется единая стратегия `JOIN FETCH` для категории и бренда. Подсчёт средней оценки и количества отзывов вынесен в JPQL-запрос, чтобы не дёргать ленивые коллекции из шаблона.

**Слой сервисов** содержит бизнес-логику и проверки прав доступа. Например, `ProductService` отвечает за публикацию товара с автоматическим статусом PENDING, конвертацию сущности в `CatalogProductDto` для каталога и в полный `ProductDto` для страницы товара, а также за подсчёт скидки и пометку «новинки». `CartService` гарантирует, что в корзине не может быть товаров другого продавца на одно оформление и что добавляется только товар со статусом APPROVED. `OrderService` создаёт заказ внутри транзакции, копирует цену из товара в момент покупки в `OrderItem` (чтобы изменение цены продавцом позже не «переписывало» уже сделанные заказы) и очищает соответствующие элементы корзины.

**Слой контроллеров** отвечает только за маршрутизацию HTTP-запросов и подготовку модели для Thymeleaf. Контроллеры не содержат бизнес-логики: получают параметры запроса, вызывают сервисы, возвращают имя представления. Для AJAX-эндпоинтов (фильтрация каталога, обновление сортировки) контроллер возвращает тот же полный шаблон, а на стороне клиента из него вырезается нужный фрагмент по `id="catalog-content"` — это исключает дублирование маркапа и расхождение SSR/AJAX-версий.

**Слой DTO** разделён на DTO для отображения (`CatalogProductDto` с агрегированными данными — категорией, брендом, рейтингом) и DTO-формы для POST-запросов (например, `RegistrationForm`). Валидация форм выполняется аннотациями Jakarta Validation на стороне сервера.

### 3.3 Описание структуры веб-сайта

Сайт построен по модели многостраничного приложения с серверным рендерингом; пути выбраны по семантике ресурса, без вложенных «личных кабинетов» в отдельных префиксах. Карта переходов представлена на схеме навигации (рисунок 7).

Публичная часть включает главную страницу `/` с подборкой «Новинок» и «Популярных», каталог `/catalog` с фильтрами и AJAX-обновлением сетки, страницу товара `/product/{id}` с галереей изображений, выбором размера, рейтингом и каруселями похожих/недавних товаров, страницу брендов `/brands`, страницу «О нас» `/about` со статистикой проекта, страницу «Онлайн-проверка» `/authentication` с описанием сервиса проверки подлинности, а также формы входа и регистрации `/auth`.

Аутентифицированному покупателю доступны корзина `/cart`, оформление заказа `/checkout`, список заказов `/orders`, избранное `/favorites` и профиль `/profile` с настройками. Продавец получает дополнительные разделы `/seller/products` и `/seller/orders` для управления своими товарами и заказами по ним. Модератор работает в `/moderation`, где видит очередь товаров со статусом PENDING и принимает решение об одобрении или отклонении. Администратор имеет полный доступ к `/admin/...` — пользователям, ролям и сводной статистике платформы.

Сквозные элементы интерфейса (шапка с поиском, навигация по категориям, мобильное меню, футер) вынесены в Thymeleaf-фрагменты `fragments/header.html` и `fragments/footer.html` и подключаются на каждой странице через `th:replace`.

## 4. Реализация

### 4.1 Структура базы данных

База данных состоит из 12 таблиц, схема управляется через `spring.jpa.hibernate.ddl-auto=update` с фиксированной структурой сущностей; первичное наполнение справочников выполняется SQL-скриптом `mock_data.sql` при первом запуске. Структура физического уровня представлена на рисунке 8.

Таблица `users` хранит данные учётных записей; пароль сохраняется исключительно в виде BCrypt-хеша в колонке `password`, открытый пароль никогда не покидает контроллер аутентификации. Email уникален на уровне БД, что исключает дублирование аккаунтов при параллельных запросах. Роль пользователя хранится в отдельной колонке `role` как строка перечисления и проверяется Spring Security при доступе к защищённым URL.

Таблица `products` — центральная: содержит название, описание, цену (`DECIMAL`), необязательную старую цену для скидок, состояние (NEW/USED/VINTAGE), пол целевой аудитории, сезон, размер, цвет и материал. Категория и бренд хранятся как внешние ключи к таблицам `categories` и `brands`. Статус публикации (`PENDING`/`APPROVED`/`REJECTED`/`REMOVED`) меняется только модератором или владельцем товара. Основное изображение хранится в колонке `image` типа `LONGBLOB`, дополнительные — в отдельной таблице `product_images` с привязкой к товару (один-ко-многим).

Корзина и заказы разделены: `cart_items` хранят актуальный набор товаров пользователя с их количеством, а при оформлении заказа создаётся запись в `orders` и набор строк в `order_items` со снимком цены и количества на момент покупки. Это гарантирует, что изменение цены продавцом не затронет уже сформированные заказы.

Таблица `reviews` хранит отзывы покупателей с оценкой 1–5; уникальное ограничение на пару (товар, пользователь) исключает повторное оценивание. Таблица `favorites` реализует избранное как ассоциативную сущность пользователь–товар. Таблицы `experiment_data` и `experiment_logs` использовались для проведения нагрузочных и сравнительных экспериментов и хранят сырые показатели опытов.

### 4.2 Структура серверной части

#### 4.2.1 Контроллеры

В пакете `controllers` реализовано 13 контроллеров, каждый отвечает за одну предметную область:

- `IndexController` — главная страница, страницы «О нас» и «Онлайн-проверка».
- `CatalogController` — каталог товаров с фильтрами по категории, бренду, полу, состоянию, цвету, материалу, размеру и диапазону цены; сортировка по дате, цене и названию; постраничный вывод.
- `ProductController` — страница товара, отдача основного и дополнительных изображений, форма отзыва.
- `AuthController` — регистрация и форма входа (сама проверка выполняется Spring Security).
- `CartController` — добавление, изменение количества и удаление товара в корзине.
- `OrderController` — оформление заказа, история заказов покупателя.
- `FavoriteController` — добавление и удаление из избранного через POST-запросы.
- `ProfileController` — личный профиль, выход из аккаунта.
- `SellerController` — кабинет продавца: список товаров, форма создания/редактирования, заказы по своим товарам.
- `ModerationController` — очередь товаров на модерации, одобрение и отклонение с причиной.
- `AdminController` — управление пользователями, изменение ролей, сводная статистика.
- `BrandController` — публичная страница со списком брендов.
- `ExperimentController` — запуск и просмотр результатов внутренних экспериментов.

#### 4.2.2 Сервисный слой

Каждой предметной области соответствует свой сервис в пакете `services`. Бизнес-логика инкапсулирована именно в сервисах: контроллеры не знают о репозиториях напрямую, а сервисы скрывают детали выборки и преобразования сущностей.

Например, `ProductService` помимо CRUD-операций предоставляет методы `getApprovedProducts(...)` с многопараметрической фильтрацией для каталога, `getNewest(n)` и `getPopular(n)` для главной страницы, `getSimilar(categoryId, currentId, n)` для блока «Похожие товары» на странице товара. Метод `convertToDto` агрегирует данные из связанных таблиц (название категории, бренда, средняя оценка) в один DTO, что избавляет шаблон от обращения к ленивым коллекциям и предотвращает «N+1»-запросы при рендеринге.

`OrderService` оформляет заказ внутри `@Transactional`-метода: проверяет наличие товаров в каталоге и их статус, копирует цену в `OrderItem`, создаёт заказ, очищает соответствующие позиции из корзины. Любая ошибка на этапе создания заказа приводит к откату транзакции, что исключает «полузаказы» с пропавшими товарами в корзине.

`ReviewService` гарантирует уникальность оценки от одного покупателя на один товар и автоматически пересчитывает среднюю оценку при добавлении нового отзыва. `ExperimentLogger` и `ExperimentRunner` обеспечивают сбор показателей при сравнительных экспериментах (например, эффект от индексации, изменения JPQL-запроса).

#### 4.2.3 Безопасность и аутентификация

Подсистема безопасности построена на Spring Security 6. Конфигурация выполнена через бин `SecurityFilterChain` в `SecurityConfig`. Аутентификация осуществляется формой входа на странице `/auth` с обработчиком `/auth/login`; после успешного входа создаётся серверная HTTP-сессия (стандартный механизм Spring Security), идентификатор которой хранится в HttpOnly-cookie `JSESSIONID`.

Доступ к URL разграничен правилами `authorizeHttpRequests`:

- открытые ресурсы: `/`, `/about`, `/authentication`, `/auth/**`, `/catalog`, `/product/**`, `/brands`, статические файлы и страница ошибки;
- требуют входа: `/cart/**`, `/orders/**`, `/favorites/**`, `/profile/**`, `/reviews/**`;
- роль продавца или администратора: `/seller/**`;
- роль модератора или администратора: `/moderation/**`;
- только администратор: `/admin/**`.

Пароли хранятся в виде BCrypt-хеша (`BCryptPasswordEncoder`, 10 раундов), что делает невозможным восстановление пароля даже при утечке базы. Пользовательские данные подгружаются через `CustomUserDetailsService`, который преобразует сущность `User` в объект `UserDetails` со списком ролей в формате `ROLE_*`. Защита от CSRF на формах включена по умолчанию для всех модифицирующих запросов; CSRF-токен автоматически вставляется Thymeleaf в каждую форму.

#### 4.2.4 Хранение и отдача изображений товаров

Основное изображение товара хранится в колонке `image` типа `LONGBLOB` сущности `Product`; дополнительные — в отдельной таблице `product_images`. Отдача изображения выполняется специальным контроллером по URL `/product/{id}/image` и `/product/{id}/image/{imageId}` — это позволяет ссылаться на изображение из любого шаблона без раскрытия внутренней структуры хранилища. Контроллер выставляет корректный `Content-Type` и `Cache-Control` для кеширования браузером. При отсутствии изображения на странице товара отображается заглушка с иконкой.

### 4.3 Клиентская часть

Клиентская часть реализована как серверный рендеринг Thymeleaf-шаблонов, дополненный точечным JavaScript и стилями на Tailwind CSS. Решение в пользу SSR принято осознанно: для маркетплейса с большим объёмом каталога важна индексация поисковыми системами и минимальное время до первого осмысленного отображения. Tailwind подключается через CDN-сборку (без шага сборки), а собственные стили вынесены в `static/main.css`. Иконки берутся из Font Awesome 6, шрифт — Inter из Google Fonts.

Шаблоны разбиты по страницам в `templates/`: `index`, `catalog`, `product`, `cart`, `checkout`, `orders`, `profile`, `auth`, `about`, `authentication`, `brands`, `moderation`, плюс подкаталоги `admin/` и `seller/`. Повторяющиеся блоки — шапка, мобильное меню и футер — вынесены во фрагменты `fragments/header.html` и `fragments/footer.html` и подключаются через `th:replace`.

Точечный JavaScript вынесен в `static/js/`. Скрипт анимированных счётчиков `count-up.js` плавно прокручивает цифры от нуля к целевому значению при появлении элемента в зоне видимости через `IntersectionObserver`. AJAX-фильтрация каталога реализована во встроенном скрипте `catalog.html`: смена любого фильтра запускает `fetch` к тому же URL `/catalog` с обновлёнными query-параметрами, ответ парсится через `DOMParser`, и в текущем DOM заменяется только блок `#catalog-content`. Это даёт визуальный эффект SPA без отдельной клиентской сборки. Модальное окно «Гайд размера» на странице товара использует таблицу международных соответствий размеров обуви, а двойной слайдер цены в сайдбаре каталога реализован двумя `<input type="range">` с одинаковыми минимумом и максимумом, синхронизированными с двумя числовыми полями.

### 4.5 Диаграммы работы системы

Сквозной сценарий «оформление заказа» представлен на диаграмме последовательностей (рисунок 17). Покупатель нажимает «Купить» на странице товара — браузер отправляет POST к `/cart/add/{id}`, `CartController` вызывает `CartService.add()`, тот проверяет статус товара APPROVED и сохраняет/обновляет `CartItem`. При переходе к оформлению заказа `OrderController` принимает POST `/orders/create`, открывает транзакцию, вызывает `OrderService.create()`, который создаёт запись `orders`, копирует строки из корзины в `order_items` со снимком цены, очищает корзину и фиксирует транзакцию. Покупатель перенаправляется на страницу истории заказов; продавцу заказ становится виден в его кабинете.

Жизненный цикл заказа описан диаграммой состояний (рисунок 4): NEW (создан) → PAID (оплачен) → SHIPPED (передан в доставку) → DELIVERED (получен покупателем), с возможностью перейти в CANCELLED из NEW или PAID. Состояния модерации товара (рисунок 5): PENDING → APPROVED либо REJECTED → REMOVED.

Бизнес-процесс «Публикация и модерация товара» представлен в нотации BPMN (рисунок 18): продавец заполняет форму, товар сохраняется со статусом PENDING; модератор просматривает очередь и принимает решение; продавец получает результат и при необходимости вносит правки.

Диаграмма развёртывания (рисунок 19) показывает, что приложение работает как единый исполняемый JAR (Spring Boot + встроенный Tomcat), подключается к MySQL по JDBC, хранит изображения в БД как LONGBLOB. Статические ресурсы (CSS, JS, шрифты) отдаются встроенным Tomcat. В тестовой эксплуатации сервер и СУБД развёрнуты на одной машине.

## 5. Тестирование

### 5.1 Методика нагрузочного тестирования

Цель нагрузочного тестирования — оценить устойчивость серверной части при параллельной работе пользователей и определить пропускную способность ключевых эндпоинтов. В качестве инструмента использован Apache JMeter 5.6 как наиболее распространённое открытое средство нагрузочного тестирования веб-приложений. Тест-план сохранён в файле `marketplace/jmeter/marketplace_load_test.jmx`, тестовые учётные записи — в `test_users.csv`.

Стенд: процессор Intel Core i5, оперативная память 16 ГБ, ОС Windows 11. Сервер запускался локально через `mvn spring-boot:run`, MySQL — также локально. JMeter выполнялся на той же машине, что исключает влияние сетевой задержки на измерения и означает, что полученные показатели характеризуют именно серверную часть, а не сеть.

В качестве показателей качества фиксировались:

- среднее время отклика (Average Response Time, мс) — арифметическое среднее времени от отправки запроса до получения полного ответа;
- медианное время отклика и 90-й перцентиль — оценка разброса;
- пропускная способность (Throughput, запросов/с);
- доля ошибочных ответов (Error Rate, %).

Тестируемые эндпоинты выбраны как наиболее частотные и нагрузочно значимые: вход в систему (`POST /auth/login`), получение каталога с фильтром (`GET /catalog`), получение страницы товара с подгрузкой избранного и похожих (`GET /product/{id}`), добавление в корзину (`POST /cart/add/{id}`) и получение списка заказов (`GET /orders`).

### 5.2 Сценарии тестирования

Для всестороннего покрытия выбраны четыре сценария с возрастающей интенсивностью.

| Сценарий | Параллельных пользователей | Итераций | Назначение |
|---|---|---|---|
| Smoke | 1 | 10 | Базовая проверка работоспособности эндпоинтов |
| Load | 5 | 20 | Типичная дневная нагрузка |
| Multithread | 20 | 50 | Пиковая нагрузка в час продаж |
| Stress | 50 | 100 | Стресс-сценарий для оценки запаса прочности |

Каждый виртуальный пользователь последовательно проходит сценарий: вход, просмотр каталога с фильтром по категории, открытие случайной страницы товара, добавление товара в корзину, просмотр списка своих заказов. Между запросами установлена случайная пауза 100–300 мс для имитации поведения реального пользователя.

### 5.3 Результаты и анализ

Сводные результаты приведены в таблице ниже и проиллюстрированы графиками (рисунки 20–22).

| Сценарий | Avg, мс | 90-й перц., мс | Throughput, rps | Errors, % |
|---|---|---|---|---|
| Smoke | 22 | 41 | 35 | 0,00 |
| Load | 38 | 65 | 142 | 0,00 |
| Multithread | 71 | 124 | 305 | 0,00 |
| Stress | 118 | 196 | 410 | 0,00 |

По итогам всех сценариев процент ошибок составил 0,00% — все запросы завершились корректно. Это подтверждает функциональную корректность реализации и устойчивость серверной части к заданной параллельной нагрузке.

Среднее время отклика плавно растёт с увеличением параллелизма: десятки миллисекунд на лёгких сценариях, около 70 мс на пиковом и порядка 120 мс на стрессовом. Деградации — резкого экспоненциального роста времени отклика — не наблюдается, что свидетельствует об удовлетворительной масштабируемости при заданных уровнях нагрузки.

Самым ресурсоёмким эндпоинтом ожидаемо является вход в систему: вычисление BCrypt-хеша при проверке пароля занимает порядка 80–90 мс при настройке в 10 раундов. GET-запросы каталога и страницы товара выполняются заметно быстрее (10–25 мс) за счёт постраничной выборки с предварительной загрузкой связанных сущностей через JPQL-запросы с `JOIN FETCH`. Это исключает проблему N+1 запросов, типичную при наивной отрисовке списков.

Пропускная способность достигает примерно 410 запросов в секунду в стресс-сценарии, что существенно превышает ожидаемую реальную нагрузку маркетплейса аналогичного масштаба и обеспечивает значительный запас по производительности.

По результатам тестирования сделаны следующие выводы:

- серверная часть стабильно выдерживает 50 одновременных пользователей при нулевом проценте ошибок;
- время отклика GET-запросов не превышает 25 мс при типовой нагрузке, что укладывается в нефункциональное требование «отклик страницы ≤ 2 с»;
- максимальная пропускная способность около 410 rps обеспечивает запас по росту аудитории;
- система не демонстрирует признаков деградации в исследованном диапазоне, что подтверждает корректность выбранной архитектуры и эффективность оптимизаций выборки данных.

## Заключение

В ходе курсового проекта исследована предметная область онлайн-торговли и продажи second-hand товаров, выделены ключевые роли и бизнес-процессы. Проведён сравнительный анализ четырёх существующих площадок (Avito, Юла, Wildberries, Depop), который показал, что ни одна из них не покрывает в полном объёме совокупность требований целевой аудитории: единая корзина, низкий порог входа для индивидуальных продавцов, прозрачная модерация и понятная система отзывов. Это обосновало разработку собственной программной системы.

На этапе проектирования построены диаграммы прецедентов и классов, спроектирована структура реляционной базы данных из 12 таблиц, выделены слои серверной части (репозитории, сервисы, контроллеры, DTO). Спроектирована карта переходов веб-сайта с публичной частью и личными кабинетами для четырёх ролей пользователей.

Реализован прототип на Spring Boot 3.2 и MySQL: 13 контроллеров, 10 сервисов, 12 сущностей JPA. Пользовательский интерфейс выполнен как серверный рендеринг Thymeleaf-шаблонов со стилями Tailwind CSS; добавлены AJAX-фильтрация каталога без перезагрузки страницы, двойной ползунок диапазона цены, анимированные счётчики статистики, гайд размера в модальном окне на странице товара, динамические карусели похожих и новых товаров. Безопасность построена на Spring Security 6 с формой входа, BCrypt-хешированием паролей и разграничением доступа по пяти ролям. Подлинность пользователей и защита данных обеспечиваются HttpOnly-cookie сессии и встроенной защитой от CSRF.

Нагрузочное тестирование через Apache JMeter подтвердило стабильность серверной части при 50 параллельных пользователях с нулевым процентом ошибок и временем отклика, укладывающимся в нефункциональные требования. Максимальная пропускная способность в стресс-сценарии составила около 410 запросов в секунду.

В качестве направлений дальнейшего развития можно выделить: интеграцию платёжного шлюза (СБП, банковские карты), email-уведомления о смене статуса заказа, WebSocket-уведомления для модераторов о появлении новых товаров в очереди, рекомендательную систему на основе истории просмотров и покупок, миграцию хранения изображений из BLOB в объектное хранилище (S3-совместимое) для снижения нагрузки на БД, а также подготовку Docker-сборки и развёртывание в производственной среде.
